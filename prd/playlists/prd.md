# Music Tagger 歌单列表页 PRD

## 1. 文档定位

本文档描述 `/playlists` 的真实单页边界。它只负责个人歌单的创建和管理，不扩展为共享歌单或协作空间。

## 2. 产品背景

当前系统已支持个人歌单模型与详情页。歌单列表页承担“看到有哪些歌单”和“创建、改名、删除歌单”的入口职责。

## 3. 产品目标

- 为用户提供个人歌单总入口。
- 支持最小歌单管理动作：创建、重命名、删除、打开详情。
- 保持歌单能力轻量稳定，不引入共享与协作复杂度。

## 4. 用户与权限

- 目标用户：已登录用户。
- 权限边界：每个用户只管理自己的歌单。
- 非目标：不提供跨用户共享、公开链接或协作编辑。

## 5. 页面定位

这是一个“歌单目录页”。

- 顶部创建新区块负责新增歌单。
- 下方卡片网格负责回看和管理现有歌单。

## 6. 页面结构

- 页面标题区：页面标题与说明。
- 新建歌单卡片：输入框 + 创建按钮。
- 歌单卡片网格：
  - 歌单名称
  - 曲目数量
  - 创建时间 / 最近更新时间
  - 打开歌单、重命名、删除动作

## 7. 页面字段定义

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 新歌单名称 | string | 是 | 创建时必填 |
| 编辑中的歌单名称 | string | 是 | 重命名时必填 |
| 歌单 itemCount | number | 是 | 当前歌单曲目数量 |
| createdAt / updatedAt | datetime | 是 | 歌单时间信息 |

## 8. 关键交互

1. 用户输入名称并创建歌单。
2. 创建成功后清空输入框并刷新列表。
3. 点击“打开歌单”进入 `/playlists/[playlistId]`。
4. 点击“重命名”后在当前卡片内进入编辑态。
5. 点击“删除”前先弹浏览器确认，再执行删除。

## 9. 页面状态

- 正常态：显示歌单网格。
- 创建中 / 保存中：对应按钮进入 pending 态。
- 空态：当没有歌单时，显示引导卡片。
- 失败态：通过 toast 反馈创建、重命名、删除失败。

## 10. 原型与 UI 设计指导

- 保持“表单卡 + 列表卡”的轻量结构。
- 每张歌单卡应优先突出名称与曲目数量。
- 编辑态应就地发生，不需要额外弹窗。
- 删除动作应弱于“打开歌单”。

## 11. 给 LLM 的输出约束

- 不要增加共享、协作、公开链接或封面编辑。
- 不要把本页做成播放页；实际点播发生在歌单详情页。
- 保持管理动作聚焦在个人歌单 CRUD。

## 12. 事实依据

- 页面当前调用 `playlists.list/create/rename/remove`。
- 歌单卡片内支持就地重命名。
- 删除歌单前使用浏览器 `confirm` 二次确认。
