# Music Tagger 后台设置页 PRD

## 1. 文档定位

本文档是面向产品原型、UI/UX 设计稿、LLM 示例代码生成的单文件 PRD。

它聚焦当前已存在的后台设置页能力，不展开工程质检、文档治理、差异报告等开发过程内容。

当前页面真实边界不是“通用系统设置中心”，而是一个明确的“转码与缓存策略配置页”。

## 2. 产品背景

Music Tagger 当前已经具备转码缓存能力，以及后台缓存治理能力：

- 管理员可以在 `/admin/cache` 里清理冷缓存、失败缓存、失效缓存
- 系统支持容量预算裁剪
- 管理台首页 `/admin` 会显示当前缓存策略摘要

但如果这些阈值只能写死在代码里，或者依赖人工改配置文件，就不利于日常运维，也不利于后续产品化演进。

因此需要一个轻量、稳定、可理解的后台设置入口，让管理员直接管理缓存治理相关阈值。

## 3. 产品目标

### 3.1 核心目标

- 提供唯一的后台配置入口，统一管理转码与缓存策略
- 让管理员能直接理解当前生效阈值，而不是依赖猜测或查代码
- 让 `/admin/cache` 和 `/admin` 使用同一份可见、可改、可即时生效的策略

### 3.2 本期成功标准

- 管理员进入 `/admin/settings` 后，可以直接看到当前生效的 3 个核心策略值
- 管理员修改并保存后，页面立即反馈成功或失败
- 新策略会被 `/admin/cache` 默认清理动作直接消费
- `/admin` 首页的缓存策略摘要与本页保持一致

### 3.3 非目标

- 不做通用“系统设置中心”
- 不做多分类设置导航
- 不做复杂权限体系
- 不做变更历史、审计日志、版本回滚
- 不做自动化定时清理任务配置

## 4. 用户与权限

### 4.1 目标用户

- 主要用户：管理员
- 使用场景：查看当前缓存治理策略、根据磁盘压力或播放习惯调整阈值

### 4.2 权限边界

- 仅管理员可访问
- 普通登录用户不可访问
- 页面不需要更细的角色拆分

## 5. 页面定位

### 5.1 页面名称

转码与缓存策略页

### 5.2 访问路由

`/admin/settings`

### 5.3 页面角色

这是一个单页配置页，不是列表页、也不是多 Tab 设置中心。

它承担两件事：

1. 回显当前生效策略
2. 修改并保存新策略

## 6. 页面结构

页面建议采用简洁的后台单页布局，自上而下分为 3 个区域：

### 6.1 页面标题区

包含：

- 页面标题：转码与缓存策略
- 一段简短说明文案，告诉用户这里管理的是缓存治理默认阈值

建议文案方向：

- 强调“统一管理”
- 强调“影响 `/admin/cache` 默认动作”
- 不要写成技术实现说明

### 6.2 当前生效策略区

建议用 3 张并列指标卡展示当前策略：

- 冷缓存阈值
- 容量预算
- 单次清理上限

下方补充辅助信息：

- 最后更新时间
- 作用范围提示，例如“作用范围：/admin/cache 默认动作”

这个区域的目标不是让用户编辑，而是让用户快速确认当前系统正在使用什么策略。

### 6.3 修改策略区

建议使用一个表单卡片，包含 3 个数字输入字段：

- 冷缓存阈值（天）
- 容量预算（GiB）
- 单次清理上限

底部包含：

- 主按钮：保存策略
- 表单校验提示区
- 一句辅助说明，例如“保存后缓存页会立即使用新的阈值和预算”

## 7. 页面字段定义

### 7.1 当前生效策略展示字段

| 字段 | 类型 | 是否必显 | 说明 |
| --- | --- | --- | --- |
| 冷缓存阈值 | integer | 是 | 当前系统用于判断“多久未命中可视为冷缓存”的天数 |
| 容量预算 | integer | 是 | 当前 ready 缓存允许占用的目标总量，展示时需转为可读单位 |
| 单次清理上限 | integer | 是 | 一次冷缓存批量清理最多处理多少条记录 |
| 最后更新时间 | datetime | 否 | 当存在设置记录时显示，否则显示 `-` |

### 7.2 修改策略表单字段

| 字段 | 类型 | 必填 | 规则 | 默认值来源 |
| --- | --- | --- | --- | --- |
| 冷缓存阈值（天） | integer | 是 | 取值范围 `1..3650` | 当前生效值 |
| 容量预算（GiB） | integer | 是 | 取值范围 `0..1024` | 当前生效值换算 |
| 单次清理上限 | integer | 是 | 取值范围 `1..500` | 当前生效值 |

### 7.3 字段说明

#### 冷缓存阈值

定义：超过指定天数未被播放命中的 ready 缓存，会被视为冷缓存。

产品理解上，它决定了系统默认“多久不用的缓存可以优先清理”。

#### 容量预算

定义：ready 缓存的总量目标上限。

产品理解上，它决定了后台做预算裁剪时，希望把缓存压回到什么容量级别。

#### 单次清理上限

定义：一次“清理未使用缓存”动作最多处理多少条记录。

产品理解上，它是一个安全阀，避免管理员一次操作影响过大。

## 8. 关键交互

### 8.1 进入页面

用户行为：

- 管理员从侧边栏进入
- 或从 `/admin`
- 或从 `/admin/cache` 的“调整策略”入口进入

系统行为：

- 加载当前生效策略
- 用当前值初始化表单

期望结果：

- 用户一眼看到当前系统阈值
- 无需额外点击即可进入修改状态

### 8.2 修改字段

用户行为：

- 直接修改数字输入框中的值

系统行为：

- 实时更新本地表单状态
- 实时判断表单是否有效

期望结果：

- 非法值时立即阻止保存
- 不要把错误延后到提交后才提示

### 8.3 保存策略

用户行为：

- 点击“保存策略”

系统行为：

- 提交新策略
- 保存中按钮禁用
- 成功后提示成功
- 失败后提示失败

期望结果：

- 成功：当前页立即回显新值
- 成功：关联页面下次读取时使用新策略
- 失败：保留用户输入，方便修改后再次提交

## 9. 页面状态

### 9.1 加载中

- 页面主体可先显示框架
- 数据区域等待当前策略返回
- 不需要复杂 loading 动效

### 9.2 正常状态

- 当前策略区展示生效值
- 表单区允许编辑
- 保存按钮可用

### 9.3 表单非法状态

- 当任一字段超出范围或不是整数时进入该状态
- 保存按钮禁用
- 页面底部显示统一校验提示

### 9.4 保存中状态

- 保存按钮进入 loading / disabled
- 禁止重复点击

### 9.5 保存失败状态

- 保留用户刚输入的值
- 通过 toast 或页内轻提示告诉用户失败原因

### 9.6 无设置记录状态

这是一个“产品上无感知”的隐式状态：

- 如果数据库中没有设置记录，页面仍然正常显示默认策略
- 不需要单独做空状态插画或空页面

## 10. 文案原则

页面文案应符合以下方向：

- 偏运维管理，但不要过度技术化
- 强调“阈值”“预算”“上限”这些管理概念
- 帮助用户理解影响，不要求用户理解底层实现

推荐文案风格：

- “统一管理冷缓存清理天数、容量预算和单次批量清理上限”
- “保存后缓存页会立即使用新的阈值和预算”
- “推荐先调整阈值，再回到缓存页执行清理”

不推荐文案风格：

- 过多出现 JSON、数据库字段名、内部实现细节
- 把页面描述成技术配置面板

## 11. 原型与 UI 设计指导

这一节用于指导 LLM 生成产品原型、界面草图或 Figma 设计稿。

### 11.1 整体风格

- 后台管理界面
- 简洁、稳定、理性
- 信息密度中等
- 重点突出“当前值”和“修改入口”

### 11.2 推荐布局

- 页面宽度中等偏窄，避免像复杂工作台那样过度铺满
- 顶部标题说明区
- 中部 3 张策略摘要卡片
- 下部单卡表单区

### 11.3 设计重点

- 当前生效策略与可编辑表单要明显分区
- 数值类信息建议使用较大字号与统一对齐
- 表单字段解释文案要短，但必须帮助用户理解该值影响什么
- 不需要做复杂图表
- 不需要做二级导航
- 不需要做多 Tab

### 11.4 原型最少需要表达清楚的内容

- 页面标题与说明
- 3 个当前值摘要卡
- 3 个输入字段
- 保存按钮
- 非法输入提示
- 最后更新时间

## 12. 给 LLM 的输出约束

如果后续要让 LLM 基于本 PRD 生成低保真原型、UI 设计稿说明或示例代码，应遵循以下约束：

### 12.1 生成原型时

- 不要扩展出“账号设置”“通知设置”“扫描设置”等未定义模块
- 只围绕转码与缓存策略这一页展开
- 不要虚构额外字段

### 12.2 生成 UI 稿时

- 使用后台管理页语义
- 保持结构清晰、输入项明确
- 不要加入与当前需求无关的统计图、趋势图、运营组件

### 12.3 生成代码时

- 页面需要包含读取当前策略和保存策略两类交互
- 表单必须有前端范围校验
- 成功和失败都要有明确反馈
- 代码结构应支持“当前值展示区”和“编辑表单区”分离

## 13. 业务规则

- 页面只服务管理员
- 页面当前只管理 3 个策略字段
- 保存成功后，新策略要被缓存页默认动作直接使用
- 页面的产品边界是“缓存治理配置”，不是“平台级系统设置”

## 14. 后续可扩展方向

这些方向不是本期范围，但可以作为后续产品演进参考：

- 增加设置变更历史
- 增加最后修改人
- 增加更多后台策略项
- 增加自动化治理任务配置
- 演进为更完整的后台设置中心

当前版本不提前设计这些内容。
